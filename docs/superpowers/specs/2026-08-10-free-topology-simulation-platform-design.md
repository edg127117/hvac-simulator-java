# 通用自由拓扑仿真平台设计

> 状态：已确认、待实施。
>
> 本文记录从现有 Gaia Java 仿真程序演进为通用自由拓扑仿真平台的正式目标、架构、数据和验收边界。本文是设计依据，不代表 Spring Boot、Vue、MySQL、TDengine、拓扑编辑器、权限或 MQTT 已经实现；当前可验证能力仍以代码、测试和 `PROJECT_STATUS.md` 为准。
>
> 本设计承接并覆盖 [`独立 HVAC 仿真平台设计`](2026-08-04-hvac-simulation-platform-design.md) 的平台级目标。原文保留为历史设计，不再作为自由拓扑平台的最终边界。Gaia 1.0 忠实转换和 Gaia 1.1 接入设计继续保持各自模型版本边界，不因平台架构调整而改变。

## 1. 背景和最终决策

当前仓库已经具备 Gaia 1.0 的纯 Java 忠实复现能力。领导后续会持续提供新的 Python 仿真模型，并要求平台能够生成建筑、设备、管路、传感器和仪表数据，保存原始数据，平滑展示曲线，再向外部中央空调经济性调试平台发送。

平台的长期目标不是把一套中央空调系统写成固定页面，也不是为某一个外部平台定制字段和流程，而是允许用户从设备库中拖入独立设备，通过水、电和控制信号端口自由连接，组成不同能量梯级利用形式的综合能源系统。中央空调设备是第一批正式设备模块，中央空调经济性调试平台是第一批外部数据使用方。

已确认采用以下路线：

1. 从第一版正式平台开始建设通用拓扑引擎，不在固定计算链外包一层伪拖拽页面。
2. 第一阶段只发布具有真实公式和可验证行为的中央空调设备模块，不提前伪造电力、燃气、蒸汽和储能模型。
3. 每个设备保持独立模块，水、电和控制信号使用共享端口和公共单位体系；不把多台设备预先绑成一个不可拆分模块。
4. 保留 Gaia 1.0、1.1 等领导版本的基准复现能力，同时允许用户基于已发布设备模块自由重组拓扑。
5. 平台先采用可拆分的模块化单体，保持引擎、应用、基础设施和前端边界；达到明确扩容条件后再拆分接口服务和计算服务。

## 2. 目标和非目标

### 2.1 平台目标

- 用户可以在大画布上拖入设备、连接端口、修改参数并保存拓扑方案。
- 设备模型、端口、参数、测点、时间能力和模型版本都有明确契约。
- 平台能够校验连接关系、编译执行图、推进仿真状态并检查质量与能量平衡。
- 仿真数据先保存到平台自己的数据库，再用于曲线、导出和外部发送。
- 计算步长、传感器采样、原始存储、图表聚合和发送速度严格分层。
- 后续 Python 版本通过基准冻结、设备转换、对照测试和版本发布进入平台，不重建平台架构。
- 第一阶段通过 MQTT 向外部平台发送；以后增加协议适配器时不修改仿真引擎。

### 2.2 第一阶段非目标

- 不允许普通用户上传 Python、Java、公式或其他可执行代码。
- 不实现真实空调设备控制，也不向 PLC、DDC 或 BMS 下发控制命令。
- 模拟传感器和仪表数据只作为输出，不参与第一阶段的闭环控制计算。
- 不实现完整管网压力和支路流量自动求解。
- 不实现 HTTP、Kafka 等正式协议适配器。
- 不实现复杂组织、部门、字段级和测点级权限。
- 不立即拆成全面微服务。
- 不声称当前 HVAC 模型具备微秒级电力暂态求解能力。

## 3. 总体架构

### 3.1 模块化单体

仓库继续采用 `engine`、`server`、`web` 三个主要边界：

```text
hvac-simulator-java
├─ engine
│  ├─ model-release        模型发布包和设备模块契约
│  ├─ device               独立设备模型
│  ├─ energy               水、电和控制信号公共定义
│  ├─ topology             拓扑图、端口和校验
│  ├─ solver               执行图、闭环迭代和守恒检查
│  ├─ measurement          传感器、仪表和测量派生
│  └─ result               仿真结果和指标定义
├─ server
│  ├─ model-management     模型版本发布和停用
│  ├─ topology-management  方案、快照和授权
│  ├─ simulation-task      任务编排和状态
│  ├─ result-storage       批次、时序数据和对账
│  ├─ delivery             发送调度、重试和确认
│  ├─ protocol-adapter     MQTT及后续协议适配
│  └─ identity             用户、权限和审计
└─ web
   ├─ app                  应用入口、路由和布局
   ├─ features             按业务能力组织的页面和逻辑
   └─ shared               UI、图表、接口客户端和公共样式
```

`engine` 不依赖 Spring、数据库、Web、MQTT 或具体外部平台。`server` 负责应用编排、持久化和协议适配。`web` 只通过稳定接口访问应用能力，不直接调用公式或数据库。

### 3.2 核心运行链路

```text
拖入设备并连线
→ 配置设备、测点和时间参数
→ 即时连接校验
→ 启动前完整校验
→ 生成不可变任务快照
→ 编译拓扑执行图
→ 按时间步计算并迭代闭环
→ 生成物理真值和模拟测量值
→ 分批写入平台数据库
→ 更新实时曲线和任务监控
→ 根据授权和发送节奏异步发送
→ 对账、重试和目标确认
```

### 3.3 未来拆分边界

第一阶段只部署一个 Spring Boot 应用，但接口层、应用层、领域层和基础设施层保持单向依赖。只有在计算任务需要独立扩缩容、任务队列成为瓶颈或多团队独立交付时，才将计算执行器拆为独立服务。拆分不改变模型包、拓扑快照、结果批次和发送消息契约。

## 4. 模型发布包和设备模块

### 4.1 两层版本

平台同时管理两种版本：

- **领导模型发布版本**：Gaia 1.0、Gaia 1.1、Gaia 1.2 等用户可见版本。
- **设备模块版本**：建筑负荷、冷水机组、水泵、冷却塔、管道、FCU、传感器和仪表各自的实现版本。

一个领导模型发布包通过模块清单固定其设备版本、默认拓扑、默认参数、时间设置、输出指标和基准资产。历史任务绑定完整清单，后续设备升级不能改变历史结果语义。

### 4.2 发布包内容

每个发布包至少包含：

- 发布版本、来源说明和状态；
- 设备模块清单及版本；
- 默认拓扑和连接；
- 全部参数默认值、单位、范围和可修改状态；
- 参数是否参与当前公式、是否锁定及其来源版本；
- 计算步长和采样能力；
- 测点、指标、来源类型和聚合规则；
- Python 参考场景、结构化结果和参考图；
- Java 对照结果、容差和已知差异；
- 适用范围、物理假设和数值限制。

已发布版本不能被同名覆盖。需要修正时发布新版本，旧版本只能停用，不能在仍有历史任务引用时物理删除。

### 4.3 Python 新版本进入流程

```text
登记原始 Python 版本
→ 在受控环境运行原程序
→ 固定输入、随机种子、时间和参考输出
→ 识别变化的公式、参数、状态和字段语义
→ 转换或升级对应 Java 设备模块
→ 运行设备级与完整场景对照
→ 人工核对图表和业务含义
→ 管理员发布新模型版本
```

新 Python 版本只升级发生变化的设备模块；未变化模块继续复用。如果原程序尚不能可靠拆分为独立设备，先只进入基准复现模式，完成边界识别和独立验证前不能伪装成自由组合模块。

### 4.4 两种运行模式

**基准复现模式**锁定模型发布包的默认拓扑、时间和基准参数，用于证明 Java 与原 Python 行为一致。允许修改的内容必须由该发布包明确声明。

**自由拓扑模式**从指定发布包复制设备模块和默认值，用户可以重新组合、增删和连接设备。新方案记录“基于 Gaia 1.1”等来源，但不再声称整个系统结果与原始固定拓扑完全一致；设备公式仍可追溯到原发布版本。

## 5. 公共能源、端口和设备契约

### 5.1 公共能源定义

第一阶段提供以下公共类型：

- 电：有功功率、电能、供电状态；
- 冷冻水、冷却水和热水：温度、质量流量、压力占位和介质属性；
- 控制信号：设定值、启停命令、模式和质量状态。

公共类型统一单位、精度、方向和符号。新增设备必须使用公共定义，不能为同一物理量自建不兼容字段。

### 5.2 设备模块职责

每个设备模块独立声明：

- 设备类型、模块版本和适用发布版本；
- 输入端口、输出端口、介质、方向和多连接规则；
- 参数定义、默认值、单位、范围和是否允许修改；
- 参数生效状态，区分参与计算、固定使用和当前未接入计算；
- 内部状态、初始条件和状态推进规则；
- 输入、输出、测点和指标；
- 支持的计算步长范围；
- 公式、限制、数值保护和错误类型。

建筑负荷、冷水机组、冷冻水泵、冷却水泵、冷却塔、管道、阀门、FCU 或 AHU、传感器和仪表均是独立模块，不把多台设备预先绑成一个系统模块。

### 5.3 传感器和仪表

传感器、电表、水表和流量计作为可拖拽模块连接到设备或介质端口。引擎始终保留内部物理真值，测量模块在真值上应用精度、偏差、噪声、分辨率和质量规则，生成模拟测量值。

第一阶段测量值只用于存储、曲线和外部发送，不反馈到控制器。理论值和模拟测量值必须使用不同指标编码和来源类型。

## 6. 自由拓扑和求解边界

### 6.1 拓扑不固定但连接受约束

用户可以自由决定设备数量、组合方式和连接关系，但不能绕过端口兼容和物理校验。平台不提供固定系统模板作为唯一执行链；模板只是可复制的起点。

### 6.2 三层校验

**连线时即时校验**检查介质、方向、供回水、多连接和端口占用。不兼容连接直接拒绝并显示中文原因。

**启动前拓扑校验**检查必需端口、闭式回路、孤立设备、无效支路、冷热源、泵、边界条件、流量或控制关系、时间能力、参数单位和测点来源。错误必须修复；警告允许确认后运行。

**运行时数值校验**检查质量守恒、能量守恒、闭环收敛、NaN、无穷值、除零、物理范围和状态跳变。异常必须记录模拟时间、设备、端口、残差和迭代次数，并在画布上高亮关联对象。

### 6.3 第一阶段水系统求解

第一阶段支持闭式水循环、质量与能量平衡、用户设定流量和控制器生成流量。拓扑编译器识别闭环并按确定顺序迭代，达到模型定义的残差容差或最大迭代次数后结束。

不实现完整压力网络和支路流量自动分配。需要该能力的拓扑必须明确提供边界流量或控制关系，不能用未经验证的默认值假装求解成功。

## 7. 最终时间设计

### 7.1 任务时间范围

任务保存仿真开始时间、结束时间、时区和初始状态时间。模型发布包提供默认值，用户可以在允许范围内修改。任务启动后时间配置进入不可变快照。

### 7.2 五层时间模型

| 层级 | 职责 |
|---|---|
| 仿真计算步长 | 公式、设备状态和能量平衡多久推进一次 |
| 传感器采样周期 | 多久生成一个模拟测点值 |
| 原始存储粒度 | 第一阶段按采样周期逐条保存，不丢弃秒级原始数据 |
| 图表聚合粒度 | 将原始数据聚合为秒、分钟或小时曲线点 |
| 数据发送速度 | 控制已入库数据以多快的现实速度发送 |

平台内部时间表示支持微秒。每个设备模块声明默认步长、最小步长和最大步长；第一阶段一个任务使用统一计算步长，所有设备都支持时才能运行。微秒表示能力不等于当前 HVAC 公式已经具备微秒级求解能力。

第一阶段要求采样周期是计算步长的整数倍，图表聚合周期是采样周期的整数倍。原始存储粒度跟随采样周期，不允许为生成分钟曲线而删除秒级原始值。

### 7.3 指标聚合

- 温度默认取区间平均值，并允许查询最小值和最大值；
- 冷负荷和功率默认取区间平均值，并保留峰值；
- 累计能耗按区间积分或增量求和；
- 开关状态和运行模式取区间末值；
- COP 使用区间总制冷量除以区间总耗电量，不能简单平均逐点 COP。

### 7.4 发送节奏

发送速度提供“发送间隔”和“回放倍速”两种配置表达，内部属于同一发送节奏能力。每条消息同时保存 `simulationTime` 和 `sentAt`；改变现实发送速度不能修改模拟时间。

## 8. 仿真任务和状态

### 8.1 不可变任务快照

任务启动前冻结：

- 模型发布版本和设备模块清单；
- 拓扑节点、端口和连接；
- 全部设备参数和默认值来源；
- 时间范围、计算步长和采样周期；
- 测点、指标和聚合规则；
- 随机种子和随机流版本；
- 数据发送是否启用及目标配置版本；
- 创建人和授权项目。

已完成任务不能直接编辑。用户需要调整时复制为新方案或新任务。

### 8.2 计算与发送状态分离

仿真状态包括草稿、校验中、等待运行、运行中、已完成、已停止和计算失败。发送状态包括未开启、等待发送、发送中、暂停、部分失败、等待重试和已完成。

仿真完成但仍有发送积压时，必须显示“仿真已完成、发送未完成”。MQTT 失败不阻止仿真继续计算和入库；原始数据入库失败时，相关批次不能发送。

### 8.3 默认发送策略

任务默认只计算、入库和展示曲线，不向外部平台发送。用户主动开启实时发送后，每批数据在入库确认后进入发送队列。已完成任务可以从数据库重新回放，不需要重新计算。

## 9. 数据存储和一致性

### 9.1 独立存储

仿真平台使用自己的 MySQL、TDengine 和文件存储，不与外部中央空调平台共用数据库。

MySQL 保存用户、角色、设备和模型元数据、拓扑方案、任务快照、批次账本、发送目标、发送记录和审计记录。TDengine 保存温度、流量、负荷、功率、COP、传感器和仪表等时序数据。文件存储保存模型包、基准资产、CSV、图表图片、批次临时恢复副本和附件。

### 9.2 通用测点结构

时序数据至少携带：

```text
runId
batchId
nodeId
deviceType
pointCode
simulationTime
sequence
value
unit
quality
modelRelease
deviceModelVersion
sourceType
```

新增公式或测点通过 MySQL 中的测点定义和通用时序记录扩展，不为每个新指标修改业务表结构。同名字段在不同版本中语义改变时必须使用不同平台指标编码。

### 9.3 一致性原则

TDengine 原始数据是仿真测点事实来源；MySQL 是任务、批次和发送状态账本。曲线和发送都读取已确认入库的数据，不直接读取计算过程中的内存结果。

每批结果保存 `batchId`、时间范围、预计数量、实际数量和校验值。处理顺序为：

```text
生成数据批次
→ 保存临时恢复副本
→ 写入 TDengine
→ 核对数量和校验值
→ MySQL 标记已入库并创建发送记录
→ 异步发送
```

稳定逻辑标识使用 `runId + nodeId + pointCode + simulationTime + sequence`。重试保持同一 `messageId`，避免重复处理。

### 9.4 对账和修复

后台对账检查缺失、重复、乱序、超时批次、MySQL 与 TDengine 状态差异以及未确认发送。缺失数据优先从临时批次副本补写；无法补写时从最近检查点或不可变任务快照重新计算。修复产生审计记录，不静默覆盖已完成历史任务。

无法自动修复的批次停止发送并进入人工处理。平台显示缺失时间范围、影响测点、错误原因和修复结果。

跨 MySQL、TDengine、MQTT 和外部平台不承诺单数据库强事务，采用批次账本、幂等标识、入库校验、对账和补偿实现可追踪的最终一致性。

## 10. 前端工作台和分层

### 10.1 大画布和浮动小窗

拓扑画布是主要工作区。左侧设备库和右侧快速参数栏均可收起；用户可全屏、缩放、平移、框选和适应画布。

仿真设置、完整参数、任务监控、结果曲线和发送详情通过应用内部的非阻塞浮动小窗打开。小窗支持拖动、缩放、最小化、最大化和关闭；最大化后成为完整功能界面。底部状态栏始终显示任务状态、模拟时间、入库数、发送数、失败数和积压数。

单击设备显示右侧快速参数，双击设备打开完整参数小窗。主流程不依赖层层下拉；固定单位和常用粒度使用按钮组，精确值使用数值或日期时间输入框。

用户选择模型发布版本或设备模块后，全部已登记参数都使用该版本默认值初始化为表单真实值，不能只写在 `placeholder` 中。参与计算且允许修改的参数可以在范围内编辑；参与计算但被基准模式锁定的参数显示真实值但保持只读；当前未接入公式的参数必须明确标记“当前不参与计算”且不能伪装成修改后会生效。参数较多时可以按设备内部业务分组或页签切换，但不能依赖难以发现的层层下拉菜单。

### 10.2 连线和动画

连线采用自动正交布线和自动避障，同时允许用户拖动拐点微调。设备拖动、画布缩放、平移和全屏切换后，连线必须继续锚定正确端口。系统提供重新整理连线和适应画布。

运行时可以使用轻量流动效果表示介质方向，暂停后停止。弹窗和画布动画不能改变计算状态，不能因视觉效果造成明显卡顿、闪烁或连线错位；应尊重减少动画的系统设置。

### 10.3 前端代码分层

前端位于仓库根目录 `web/src`，不是 Java 的 `src/main/java`：

```text
web/src
├─ app
│  ├─ router
│  ├─ layout
│  └─ permission
├─ features
│  ├─ topology-modeling
│  ├─ model-release
│  ├─ simulation-task
│  ├─ result-analysis
│  ├─ data-delivery
│  └─ user-management
└─ shared
   ├─ ui
   ├─ chart
   ├─ api
   ├─ validation
   ├─ types
   └─ styles
```

每个复杂业务能力内部按 `pages`、`components`、`state`、`application`、`model`、`ports` 和 `adapters` 分层。页面和状态层不能直接调用 Axios；外部接口由 `ports` 定义，HTTP 实现在 `adapters`。视觉改版主要影响页面、组件和共享样式，不能改变拓扑、任务和发送业务规则。

## 11. 结果、曲线和导出

结果分析在仿真运行时显示增量曲线，任务完成后显示完整曲线。核心面板包括温度、负荷、功率、COP 和自选测点；模型版本可以登记专属面板，但不能混淆理论值和模拟测量值。

曲线支持图例切换、时间缩放、测点筛选和服务端聚合。前端不能一次加载数百万条原始记录。图表使用统一指标定义中的名称、单位、精度、来源类型和聚合规则。

导出至少支持任务快照、拓扑、原始时序 CSV、聚合结果和图表图片。所有导出必须包含模型版本、任务编号、时间范围、单位和生成时间。

## 12. 数据发送和协议适配

### 12.1 统一发送链路

```text
TDengine 已确认原始数据
→ 统一发送消息
→ 发送调度服务
→ 协议适配器
→ 外部平台
```

发送调度服务负责读取已入库数据、现实发送节奏、暂停、重试、积压、对账和目标确认。协议适配器只负责连接、字段映射、编码和协议操作。

### 12.2 第一阶段 MQTT

第一阶段只实现 MQTT 发送适配器。中央空调平台实现 MQTT 接收和消费，不需要实现发送适配器。以后增加 HTTP、Kafka 或其他协议时，只新增适配器和目标字段映射，不修改仿真引擎、设备公式或内部结果结构。

### 12.3 统一消息

```json
{
  "schemaVersion": "1.0",
  "messageId": "稳定唯一编号",
  "sourceType": "SIMULATION",
  "runId": "仿真任务编号",
  "modelRelease": "Gaia 1.1",
  "simulationTime": "模拟时间",
  "sentAt": "实际发送时间",
  "device": {
    "nodeId": "拓扑节点编号",
    "deviceType": "CHILLER",
    "deviceModelVersion": "1.1"
  },
  "points": [
    {
      "pointCode": "system_power_kw",
      "value": 168.4,
      "unit": "kW",
      "quality": "GOOD"
    }
  ]
}
```

内部消息保持通用。外部平台的 Topic 和字段差异通过目标配置与映射处理，不能把某个中央空调平台的字段写进设备公式。

MQTT PUBACK 只能证明 Broker 接收，不能证明目标平台已经入库。若目标平台支持应用确认，通过独立确认主题返回 `messageId`；否则状态只能标记“Broker 已接收”，不能声称“目标已确认”。

## 13. 用户、权限和安全

第一阶段只提供两个角色：

| 角色 | 权限 |
|---|---|
| 平台管理员 | 用户管理、设备和模型发布、发送目标配置、全部任务管理、异常修复和审计查看 |
| 仿真用户 | 修改被授权方案、搭建拓扑、运行仿真、查看曲线、导出结果，并向已授权目标发送 |

不设置只读查看用户，因为平台最基础能力就是允许用户修改和运行仿真。仿真用户只能修改自己创建或被授权的方案；已完成任务不可直接修改，只能复制。

普通用户不能上传代码或公式。发送默认关闭，目标必须由管理员配置和授权。数据库密码、Broker 密码、Token 和私钥通过外部安全配置提供并加密保存，不进入模型包、普通日志或版本库。

模型发布、任务启动、停止、发送、重试和人工修复均保存审计记录。

## 14. 异常处理和监控

- 计算失败时停止后续计算，保留已确认入库的数据和准确错误位置。
- 原始数据入库失败时，相关批次不得创建发送任务。
- MQTT 失败不影响计算和入库，失败消息按退避策略重试。
- 用户可以单独暂停发送，不暂停仿真。
- 达到重试上限后进入失败记录，允许管理员或任务所有者重新发送。
- 停止任务不删除已经生成的数据。
- 任务监控同时显示计算、入库、曲线和发送状态。

日志和监控至少按 `runId`、`batchId`、`nodeId`、模型版本和模拟时间关联。错误信息使用中文说明问题、影响范围和恢复方式，不向普通用户暴露凭据和内部堆栈。

## 15. 测试和验收

### 15.1 设备模型

验证参数、单位、端口、公式、状态、零负荷、额定负荷、超限、非法数值和时间步长。Gaia 设备必须与对应 Python 版本的冻结场景进行全时间步对照，容差按指标分别定义。

### 15.2 拓扑和求解

验证合法与非法连接、开放与闭式系统、孤立设备、错误介质、质量与能量守恒、闭环收敛和不收敛。设备拖动、画布缩放和平移后必须自动检查端口锚定和连线路径。

### 15.3 时间和数据

验证计算次数、采样点数量、时间戳、秒级原始入库、分钟聚合、指标聚合算法，以及发送速度变化时 `simulationTime` 不变。

### 15.4 一致性和基础设施

模拟 TDengine 中断、MySQL 状态失败、重复写入、缺失、乱序、服务重启、MQTT 断开和目标未确认，验证检测、补偿、重试和审计。

### 15.5 完整链路

必须覆盖：

```text
搭建拓扑
→ 参数和物理校验
→ 运行仿真
→ 原始数据入库
→ 浮动曲线实时显示
→ MQTT 发送
→ 目标确认或明确停在 Broker 已接收
→ 异常重试和对账
```

### 15.6 规模和视觉

至少建立两个规模场景：

- 100 个测点、1 分钟采样、运行 24 小时，共 14.4 万条原始数据；
- 100 个测点、1 秒采样、运行 24 小时，共 864 万条原始数据。

具体响应时间在部署硬件确定后冻结。视觉验收人工检查浮动小窗动画、连线准确性、中文字体、曲线可读性和大量设备下的画布操作。
