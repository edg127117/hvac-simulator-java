# 历史状态隔离与自动防复发设计

> [!IMPORTANT]
> 文档类型：设计记录<br>
> 生命周期：冻结历史快照<br>
> 当前状态：[PROJECT_STATUS.md](../../../PROJECT_STATUS.md)<br>
> 历史目录：[docs/superpowers](../)<br>
> 使用限制：本文记录本次任务确认的设计，不用于判断功能当前是否已实现或已验证。

## 1. 背景与问题

仓库已经明确：当前能力必须以代码、测试、Git 和 `PROJECT_STATUS.md` 为准，旧设计和旧计划不能推翻当前证据。但仅有阅读规则仍无法消除以下风险：

- 旧文档正文保留“未实现”“待开发”“尚未合并”等任务当时的描述，全文搜索或单独阅读时仍可能被误认为当前状态；
- `AGENTS.md` 等当前入口可能长期保存动态能力清单。例如当前规则仍把 Spring Boot、Vue、MQTT 和 Gaia 1.1 描述为待实施，但这些能力已经出现在代码、测试和 `PROJECT_STATUS.md` 中；
- 历史文档缺少统一、醒目的类型和使用限制，阅读者无法快速识别它是历史快照；
- 没有自动检查来约束历史标识、状态入口、PR 文档同步和冻结后的回写。

本设计解决的是“已经完成的任务仍被旧记录判断为未实现”，不是单纯阻止编辑旧文件。

## 2. 方案选择

### 2.1 方案 A：只依靠文字规则

保持现有结构，只在 `AGENTS.md` 提醒优先读取当前状态。改动最小，但搜索仍会命中旧状态，当前入口也可能再次积累动态事实，不能形成自动防复发机制。

### 2.2 方案 B：删除或重写全部历史状态

从设计和计划中删除所有未勾选项、未来时态和当时的未实现描述。误判风险最低，但会破坏任务当时的真实上下文，失去设计演进、取舍和实施证据。

### 2.3 方案 C：状态隔离、统一警告和自动 Guardrails

保留历史设计与计划的任务快照，统一增加醒目历史警告；清除当前入口中的动态能力状态；状态判断和检索默认排除历史目录；通过本地 Hook、GitHub CI 和 PR 模板验证文档类型、链接、冻结和状态同步。

采用方案 C。它同时保留历史证据和当前状态唯一性，并能自动阻止同类问题再次进入 `main`。

## 3. 文档职责

### 3.1 当前状态入口

- `AGENTS.md` 只保存长期硬约束、证据顺序、文档路由和自动检查要求，不保存“某功能当前已实现或未实现”的动态能力清单。
- `PROJECT_GUIDE.md` 保存稳定项目地图、运行入口、数据链路和当前正式设计导航；短期任务完成情况仍由 `PROJECT_STATUS.md` 承担。
- `PROJECT_STATUS.md` 是人可读的当前完成、未完成、验证层级、风险和下一步入口。其结论仍必须能由当前代码、测试、Git 和实际验证支持。

发现三个当前入口彼此冲突时，先核验代码、测试和 Git，再修正当前入口；不得回写历史正文制造一致。

### 3.2 历史设计和实施计划

`docs/superpowers/specs` 与 `docs/superpowers/plans` 记录任务当时的设计和实施安排。每份文件开头必须包含统一可见块：

```markdown
> [!IMPORTANT]
> 文档类型：设计记录或实施计划<br>
> 生命周期：冻结历史快照<br>
> 当前状态：[PROJECT_STATUS.md](../../../PROJECT_STATUS.md)<br>
> 历史目录：[docs/superpowers](../)<br>
> 使用限制：本文记录任务当时的设计或计划，不用于判断功能当前是否已实现或已验证。
```

未勾选步骤、未来时态和当时的未实现描述允许保留为历史快照，但状态评估、范围盘点和下一步规划不得以这些内容为当前证据。

### 3.3 当前正式设计导航

`PROJECT_GUIDE.md` 可以把某份冻结设计列为当前正式设计，用于说明仍有效的架构和兼容边界。该白名单不改变文档的历史属性，也不允许用其中的完成状态描述代替 `PROJECT_STATUS.md`。

## 4. 一次性迁移

本设计对 [`文档生命周期与当前状态判定设计`](2026-08-12-document-lifecycle-and-current-state-design.md) 的“冻结后绝不回写”规则作一次受控替代：

1. 为迁移前已经存在的全部设计和计划补充统一可见块；
2. 删除历史文档中冒充当前入口的动态能力总表、当前完成清单或分支合并状态，改为指向 `PROJECT_STATUS.md`；
3. 保留设计决策、接口合同、兼容边界、验收标准、实施步骤和未勾选项，不把历史计划重新勾选为完成；
4. 修正 `AGENTS.md`、`PROJECT_GUIDE.md`、`PROJECT_STATUS.md` 中与当前代码、测试和 Git 明确冲突的状态描述；
5. 迁移 PR 合并后，全部既有设计和计划重新冻结，后续只能新增带日期文件承接变化。

自动检查以“基线分支是否已经包含 Guardrails 启用标识”区分一次性迁移和后续普通 PR：首次迁移允许受控修改既有历史文件；启用标识进入 `main` 后，修改、删除或重命名既有历史文件全部失败。删除启用标识本身同样失败。

## 5. 状态检索隔离

涉及当前能力、完成情况、范围、风险或下一步时：

1. 先检索当前生产代码、测试和 Git；
2. 再读取 `PROJECT_STATUS.md` 和 `PROJECT_GUIDE.md`；
3. 默认排除 `docs/superpowers/specs` 与 `docs/superpowers/plans`；
4. 只有用户明确要求追溯历史、核对设计理由或验证兼容边界时，才读取历史目录；
5. 即使读取当前正式设计，也只能提取架构和兼容决策，不能提取其中的历史完成状态作为当前结论。

`AGENTS.md` 必须把该顺序写成任务入口硬规则，避免全文搜索先命中旧记录。

## 6. Repository Guardrails

### 6.1 PowerShell 检查入口

新增 `scripts/Test-RepositoryGuardrails.ps1`，支持完整工作树、暂存差异、PR 基线和 PR 正文四类输入，统一检查：

- 全部设计和计划存在正确的“文档类型”“生命周期”“当前状态”“历史目录”“使用限制”；
- 两个相对链接实际存在；
- Guardrails 启用后，既有历史文件未被修改、删除或重命名，新文件可以新增；
- `PROJECT_GUIDE.md` 当前正式设计导航中的路径存在；
- `AGENTS.md` 不再包含动态能力完成表，并保留状态检索隔离规则；
- PR 正文包含状态影响、检查范围和文档同步结论。

脚本失败时返回非零退出码，并输出具体文件和缺失规则，不自动修改文件。

### 6.2 本地 Hook

版本化 `.githooks/pre-commit` 调用 Guardrails 的暂存模式；新增安装脚本只为当前仓库设置 `core.hooksPath=.githooks`。Hook 在提交前发现缺失历史警告、冻结文件回写或当前入口违规时阻止提交。

Hook 只能约束已安装它的本地仓库，因此不能替代 CI。

### 6.3 GitHub CI 与合并保护

新增 `.github/workflows/repository-guardrails.yml`，在 pull request 和 `main` 推送上运行同一脚本及自动化测试。工作流检查名固定，合并后在 GitHub 分支保护或 Ruleset 中设为 required status check。

只有工作流存在但未设为 required 时，GitHub 仍可能允许管理员合并失败 PR；因此“自动阻止合并”的验收必须同时包含 CI 通过和 required check 已启用的证据。

### 6.4 PR 模板

新增 `.github/pull_request_template.md`，要求每个 PR 明确填写：

- 状态影响：新增、完成、部分完成、未验证或无状态变化；
- 检查范围：实际检查的代码、测试、Git 和外部环境；
- 文档同步：是否更新 `PROJECT_STATUS.md`、`PROJECT_GUIDE.md`，或为何无需更新；
- 历史文档：是否只新增记录，未回写冻结文件；
- 验证分级：自动化测试、本地运行、外部联调、现场验证分别说明。

CI 只验证必需标题和选择项存在，不判断业务结论真假；结论仍由审查者依据证据确认。

## 7. 自动化测试

新增 `scripts/tests/Invoke-RepositoryGuardrailTests.ps1`，至少覆盖：

- LF、CRLF、UTF-8 BOM 三种换行/编码格式；
- 设计或计划缺少类型、生命周期、当前状态链接、历史目录链接、使用限制；
- 链接目标不存在；
- 新增合规历史文件允许通过；
- Guardrails 启用后修改、删除、重命名冻结文件均失败；
- 删除或篡改启用标识失败；
- `AGENTS.md` 缺少状态检索隔离规则或重新加入动态能力清单；
- PR 正文缺少状态影响、检查范围、文档同步或验证分级；
- 本次迁移模式只在基线未启用 Guardrails 时有效，后续不能再次开启。

测试使用临时 Git 仓库或隔离 fixture，不修改真实工作树。

## 8. 实施与交付边界

本设计拆为一个实施计划、一个任务分支和一个 PR，顺序为：

1. 先完成当前入口审计和历史文档一次性迁移；
2. 再加入 Guardrails 脚本、测试、Hook、CI 和 PR 模板；
3. 使用新 Guardrails 自检本 PR；
4. 推送并创建 PR；
5. PR 合并后启用 required status check，再验证失败场景确实不能合并。

本任务不修改 Java、Vue、仿真公式、参数、参考资产或业务行为；不运行与文档治理无关的 Java、前端和仿真测试。

## 9. 验收标准

- 当前入口不存在与代码、测试和 Git 明确冲突的动态状态描述；
- 全部历史设计和计划都有统一可见警告和有效链接；
- 状态评估规则默认排除历史目录；
- 历史正文中的动态能力总表和当前分支状态已移除，设计与计划证据保留；
- Guardrails 自动化测试全部通过；
- 本地 Hook 能阻止违规暂存提交；
- GitHub CI 能识别合规和违规 PR；
- required status check 启用后，违规 PR 无法进入 `main`；
- PR 模板强制记录状态影响、检查范围、文档同步和验证分级；
- `git diff --check` 通过，差异只包含本任务授权的文档治理和自动化文件。
