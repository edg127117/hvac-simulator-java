# 独立 HVAC 仿真平台设计

> 状态：已确认、待实施。
>
> 本文记录从 Gaia 1.0 Java 仿真程序演进为独立正式仿真平台的目标、边界和验收标准。本文是设计依据，不代表 Spring Boot、Vue、数据库、权限或 MQTT 功能已经实现；当前可验证能力以 `PROJECT_STATUS.md`、代码和测试为准。

## 1. 背景与目标

当前项目已经完成 Gaia 1.0 的 Java 忠实转换，能够以基准气象或 Java 合成气象运行仿真，并生成 CSV 与温度、负荷、功率和 COP 图表。后续领导会持续提供 Python 模型，项目需要在保留基准复现能力的同时，建设可配置、可追溯、可视化、可存储和可发送的独立仿真平台。

正式平台的第一阶段目标是：

1. 以 Gaia 1.0 为首个正式模型版本。
2. 允许用户通过页面创建、运行和查看仿真任务。
3. 将任务、参数和结果先保存到仿真平台自己的数据库。
4. 从已入库结果创建独立发送任务，通过 MQTT 回放到空调平台。
5. 保留未来增加模型版本、输出指标、协议适配器和独立计算 Worker 的演进能力。

正式平台不改变 Gaia 1.0 忠实基准。物理模型修正、控制策略改进或新 Python 版本必须形成新的模型版本，不能静默覆盖历史行为。

## 2. 项目和实施边界

### 2.1 当前仓库第一阶段

`hvac-simulator-java` 负责建设独立仿真平台，包括：

- Spring Boot 后端与 Vue 3 前端；
- 用户与最小权限；
- 模型版本和参数定义；
- 仿真任务、参数快照和异步执行；
- MySQL 管理数据和 TDengine 时间序列；
- 温度、负荷、功率和 COP 图表；
- CSV、PNG 导出；
- 数据发送任务；
- MQTT 发送适配器及发送侧契约测试。

### 2.2 空调平台第二阶段

`iot-platform-demo` 保持独立项目。其后续任务负责：

- 订阅独立仿真主题；
- 识别仿真数据来源；
- 解析、校验和去重；
- 保存仿真数据；
- 在查询中区分真实数据和仿真数据；
- 与仿真平台完成端到端联调。

当前仓库只定义发送契约，不直接修改或复制 `iot-platform-demo` 的代码、业务状态和项目事实。第二阶段开始前必须重新读取并遵守该仓库自己的规则和当前状态。

### 2.3 第一阶段不包含

- 在页面上传并直接执行 Python 文件；
- 修改 Gaia 1.0 公式以改善物理合理性；
- 多任务曲线对比；
- 仿真任务从中间时间点断点续算；
- 部门、菜单、数据范围和自定义角色系统；
- HTTP、Kafka 等非 MQTT 发送实现；
- 全面微服务、服务网关和分布式事务体系；
- 空调平台 MQTT 接收端代码；
- 自动数据保留周期、备份和灾备方案；
- 现场实测数据标定和物理工程验收。

## 3. 总体架构

### 3.1 方案选择

第一阶段采用可拆分的模块化单体。与接口服务和计算 Worker 立即分离、全面微服务相比，该方案保留清晰边界，同时减少第一阶段部署和运维组件。

```text
浏览器
  ↓
Vue 3 前端
  ↓
Spring Boot 模块化单体
├─ 用户与权限
├─ 模型版本与参数定义
├─ 仿真任务
├─ 结果查询与导出
├─ 数据发送任务
└─ 协议适配器
  └─ MQTT
  ↓
MySQL + TDengine + MQTT Broker
```

### 3.2 仓库模块

计划将代码组织为：

```text
hvac-simulator-java
├─ hvac-simulator-engine
│  └─ 纯 Java 仿真引擎
├─ hvac-simulator-server
│  └─ Spring Boot、任务、数据库、权限和协议适配
└─ hvac-simulator-web
   └─ Vue 3 前端
```

第一阶段只部署一个 Spring Boot 后端。`engine` 不依赖 Spring、数据库、Web 或 MQTT；`server` 依赖 `engine`，负责平台编排。现有仿真公式、基准资产和一致性测试迁入 `engine` 时必须保持行为不变。

### 3.3 后端内部边界

```text
接口层
  ↓
应用服务层
├─ 模型版本服务
├─ 仿真任务服务
├─ 结果服务
├─ 发送任务服务
└─ 用户权限服务
  ↓
领域与端口
├─ SimulationExecutor
├─ ResultRepository
├─ SimulationDataSender
└─ DeliveryCursorRepository
  ↓
基础设施适配器
├─ 进程内 Gaia 执行器
├─ MySQL
├─ TDengine
└─ MQTT
```

接口层不能直接调用具体公式，仿真引擎不能直接访问数据库或 MQTT，数据发送模块只能读取已入库结果，不能重新运行仿真公式。

## 4. 模型版本和运行模式

### 4.1 模型版本原则

Gaia 1.0 是首个正式模型版本。每个模型版本至少包含：

- 版本编码和中文名称；
- 来源说明和模型状态；
- 参数定义及默认值；
- 指标定义及单位；
- 基准输入和预期结果；
- Java 实现版本；
- 结果结构版本；
- 发布时间和发布人。

已发布模型不能被同名覆盖。模型升级后，历史任务继续绑定原模型版本和结果结构版本，保证可以复现。

### 4.2 新 Python 版本进入流程

领导提供新版 Python 后采用以下流程：

1. 离线保存来源说明并运行 Python。
2. 冻结基准输入、输出和参考图。
3. 分析参数、公式、状态、单位和输出字段变化。
4. 在纯 Java 引擎中新增或升级模型实现。
5. 完成全时间步一致性测试和人工图表核对。
6. 测试通过后由管理员发布新模型版本。

平台页面不直接上传或执行 Python。未经一致性验证的模型不能作为已发布版本供普通用户创建任务。

### 4.3 基准模式

基准模式用于验证 Java 与冻结 Python 结果一致：

- 使用模型版本绑定的冻结气象输入；
- 锁定时间范围、时间步长和全部模型参数；
- 不允许通过前端或接口修改锁定值；
- 结果用于回归测试和领导对照确认。

### 4.4 场景模式

场景模式使用 Java 原生气象和 Java 仿真引擎：

- 使用模型版本默认值创建参数表单；
- 只允许修改当前模型已接入公式的参数；
- 保存完整参数快照和随机种子；
- 相同模型版本、参数、时间范围和随机种子应产生可重复结果。

## 5. 参数目录和页面结构

### 5.1 参数定义

模型参数目录至少保存：

```text
参数编码
中文名称
所属分组
数据类型
默认值
单位
最小值
最大值
小数精度
是否必填
是否可编辑
是否参与当前公式
生效模式
排序
中文说明
```

前端根据参数目录动态生成普通数值、文本、枚举和布尔表单。新增普通参数时优先只登记参数定义，不修改前端；特殊交互控件另行设计。

### 5.2 十组折叠表单

新建仿真页面采用以下十组结构：

| 折叠分组 | 参数范围 |
|---|---|
| 基础设置 | 模型版本、运行模式、仿真开始时间、结束时间、仿真步长、随机种子 |
| 气象参数 | 纬度、经度、设计干球温度、设计湿球温度、气象生成模式 |
| 建筑参数 | 建筑面积、空调面积、层数、层高、各朝向窗墙比、传热系数、SHGC、热容、热阻、渗透换气次数 |
| 内部负荷 | 人员密度、人员显热与潜热、照明功率密度、设备功率密度、人均新风量 |
| 冷机参数 | 冷机容量、额定 COP、冷冻水和冷却水供回水温度、PLR 曲线系数 |
| 水泵参数 | 冷冻水泵和冷却水泵的额定流量、扬程、水泵效率、电机效率 |
| 冷却塔参数 | 额定流量、风机功率、逼近温度 |
| 管道参数 | 冷冻水和冷却水管道的管径、长度、保温厚度、导热系数等 |
| FCU 参数 | FCU 数量、风量、风机功率、水流量、水侧压降 |
| 控制参数 | 制冷设定温度、制热设定温度、死区、冷冻水温度策略 |

每组允许继续划分基础参数和高级参数。页面提供“恢复本组默认值”和“恢复全部默认值”。数据发送频率不属于仿真参数，放在仿真结果的发送设置中。

### 5.3 参数生效状态

页面必须区分：

- `当前模型生效`：场景模式允许修改；
- `仅合成气象模式生效`：只在对应模式开放；
- `当前模型未启用`：展示但禁止修改，并说明未接入原因。

前端禁用不能代替后端校验。接口提交锁定参数或未启用参数的修改值时，后端必须拒绝。

### 5.4 Gaia 1.0 当前未接入主链的参数

下列参数需要进入完整参数目录，但不能表现为修改后会影响当前结果：

| 分组 | 未接入或未影响当前结果的参数 | 说明 |
|---|---|---|
| 气象 | 经度、设计干球温度、设计湿球温度 | 当前生成公式未读取；基准模式不读取任何可编辑气象参数 |
| 建筑 | 总建筑面积、每层体积、四向窗墙比、等效热阻 | 当前使用固定墙、窗和屋面面积，热阻未进入温度更新 |
| 内部负荷 | 人员潜热、人均新风量 | 潜热结果未进入主循环；新风负荷方法为预留能力 |
| 冷机 | 冷却水额定供水温度 | 运行温度由湿球温度和冷却塔公式产生，停机值为固定兼容值 |
| 冷却水管道 | 管径、长度、保温厚度、导热系数等 | 当前只计算冷冻水管道热量 |
| 冷却塔 | 额定流量 | 当前只使用额定风机功率和逼近温度 |
| FCU | 额定风量、额定水流量、水侧压降 | 当前只使用 FCU 数量和单台风机功率 |
| 控制 | 制热设定温度、冷冻水温度重置策略 | 当前只有供冷逻辑，冷冻水供水温度固定 |
| 描述信息 | 冷机类型、末端类型、管网拓扑、管材、泵控制方式等 | 只用于设备和版本说明 |

纬度是特殊参数：原 Python 将 `30.5°` 写入气象公式，没有读取参数对象；当前 Java 合成气象实现已经读取纬度，因此纬度标记为“仅合成气象模式生效”。

## 6. 仿真任务

### 6.1 任务创建和锁定

用户保存未运行配置时形成草稿。任务进入队列前，后端生成不可变参数快照，至少包含：

- 模型版本和结果结构版本；
- 运行模式；
- 时间范围和步长；
- 随机种子；
- 全部模型参数及单位；
- 创建人和创建时间。

任务开始后不能直接修改。用户需要调整时使用“复制为新任务”，在新草稿中修改并重新运行。参数快照、结果、图表和发送任务必须始终通过同一个 `runId` 对应。

### 6.2 状态

```text
草稿 → 排队中 → 运行中 → 已完成
                  ├→ 已取消
                  └→ 失败
```

第一阶段允许多个用户提交任务，但默认只有一个任务实际计算，其余任务保持排队。并行计算数作为管理员配置保留，默认值为 1。

### 6.3 执行方式

第一阶段使用 MySQL 中的持久任务状态和进程内执行器，不把唯一运行状态保存在内存或本地文件。执行器领取任务后调用纯 Java `engine`，分批写入 TDengine，并更新进度和当前仿真时间。

用户取消运行中的任务时，执行器在安全检查点停止。部分结果不能标记为完成，并由后台清理。平台异常重启后，原“运行中”任务标记为“异常中断/失败”，第一阶段由用户复制后重新运行，不从中间状态续算。

执行必须具备幂等边界，同一个任务不能被两个执行器同时领取，也不能因重复调度生成两套可见完成结果。

## 7. 数据存储

### 7.1 MySQL 职责

MySQL 保存：

- 用户、角色和登录会话；
- 模型版本、参数定义和指标定义；
- 仿真任务和不可变参数快照；
- 任务进度、错误摘要和结果概况；
- MQTT 连接配置的非敏感部分；
- 发送任务、发送游标、重试状态和消息标识；
- 关键操作审计记录。

数据库密码和 MQTT 密码不进入版本库或普通审计内容，通过环境变量或外部安全配置提供。

### 7.2 TDengine 职责

TDengine 保存逐时间点结果。第一阶段采用“核心宽表 + 扩展指标”结构：

```text
核心结果
├─ timestamp
├─ runId、modelVersion等标签
├─ 干球温度、湿球温度、太阳辐射
├─ 室内温度、冷负荷
├─ 冷机、水泵、冷却塔、FCU及系统总功率
├─ PLR、COP
└─ 水温、管道热量等Gaia核心结果

扩展指标
├─ timestamp
├─ runId、modelVersion、metricCode等标签
└─ metricValue
```

扩展指标只保存未进入核心结果表的新指标，不重复保存同一完整分钟结果。MySQL 保存 `metricCode` 对应的中文名称、单位、精度、分组和展示方式。

新模型增加普通指标时，只登记指标定义并写入扩展指标结构。只有指标经过单独设计成为全平台通用核心字段时，才调整核心表。

### 7.3 一致性和删除

- MySQL 不重复保存完整分钟时间序列；结果概况可以保存派生汇总值。
- 仿真任务只有在全部必要结果成功入库后才能标记完成。
- MySQL 或 TDengine 写入失败时记录失败范围，不向用户展示为完整结果。
- 删除任务先软删除元数据；TDengine 结果由后台安全清理。
- 正在运行、正在发送或仍被发送任务引用的数据不能直接清理。
- 第一阶段不自动按保留天数删除数据，自动保留策略另行设计。

## 9. 结果查询、图表和导出

### 9.1 结果概况

结果详情至少显示：

- 仿真时间范围和总数据点数；
- 峰值冷负荷；
- 峰值系统功率；
- 冷机运行时平均 COP；
- 累计耗电量；
- 任务执行耗时；
- 模型版本和结果结构版本。

平均 COP 只统计冷机运行时间，不把停机零值计入平均值。累计耗电量按每个时间步的系统功率积分计算，计算方法和单位必须在页面说明。

### 9.2 图表

第一阶段提供四组连续曲线：

1. 温度；
2. 冷负荷；
3. 系统及设备功率；
4. COP。

图表支持鼠标提示、图例切换、时间范围缩放和自定义时间查询。功率图允许切换系统总功率、冷机、水泵、冷却塔和 FCU。停机时功率和 COP 按 Gaia 兼容零值连续显示，不能改成只画非零散点。

### 9.3 数据和文件导出

- 分钟数据分页查询；
- 完整结果导出为 UTF-8 CSV；
- 当前图表导出为中文 PNG；
- 导出的 CSV 和 PNG 必须来自同一任务的已入库结果，不能重新计算；
- 第一阶段不支持多任务曲线叠加比较。

## 10. 数据发送和协议适配

### 10.1 发送与仿真分离

仿真参数决定生成什么数据，发送参数只决定已入库数据如何传输。流程为：

```text
配置仿真 → 运行并入库 → 查看结果 → 创建发送任务 → 通过协议适配器发送
```

同一份仿真结果可以建立多个发送任务，使用不同时间范围和速度，不需要重新仿真。发送模块不能读取草稿、运行中或失败任务的不完整数据。

### 10.2 统一发送接口

后端提供与具体协议无关的发送端口：

```java
public interface SimulationDataSender {
    void send(SimulationMessage message);
}
```

第一阶段实现 `MqttSimulationDataSender`。未来增加 HTTP 或 Kafka 时新增适配器和相关配置、测试，不修改仿真引擎、任务结果或数据库核心结构。

### 10.3 MQTT 规则

- 默认 Topic：`simulation/hvac/data/up`；
- QoS：1；
- Retained：`false`；
- Broker、Topic、用户名、密码和 QoS 由管理员配置，不写死在代码；
- 仿真数据不使用真实设备 `device/data/up` 主题；
- 多个仿真任务可以共用 Topic，由 `runId` 区分。

QoS 1 提供至少一次传递。发送游标在收到 Broker 的 PUBACK 后推进，但 PUBACK 不等于空调平台已经完成业务入库，因此接收端仍必须根据 `messageId` 幂等去重。

### 10.4 消息结构

```json
{
  "schemaVersion": "1.0",
  "messageId": "唯一消息编号",
  "sourceType": "SIMULATION",
  "simulated": true,
  "runId": "仿真任务编号",
  "modelVersion": "Gaia 1.0",
  "simulationTime": "2024-07-01T08:00:00+08:00",
  "sentAt": "2026-08-04T15:00:00+08:00",
  "metrics": {
    "room_temperature": 25.1,
    "cooling_load_kw": 820.5,
    "system_power_kw": 168.4,
    "chiller_cop": 5.72
  }
}
```

身份字段属于稳定消息信封。`metrics` 根据模型版本和目标字段映射动态生成。仿真平台保存全部结果，只发送目标平台支持的指标；未映射指标仍可在仿真平台查询和展示。

消息时间必须带明确时区。`simulationTime` 是数据代表的模拟时间，`sentAt` 是现实发送时间，两者不能混用。

### 10.5 发送速度和状态

发送任务默认覆盖完整仿真结果，也允许选择结果时间范围。`每分钟发送条数` 取值 1～600，默认 60：

| 配置 | 目标发送速度 |
|---:|---|
| 1 | 每个现实分钟 1 条 |
| 60 | 每秒约 1 条 |
| 120 | 每秒约 2 条 |
| 600 | 每秒约 10 条 |

每条消息始终代表一个独立仿真时间点，不合并、不降采样。发送速率是平均目标，不承诺硬实时精度；网络重试期间不能为追赶进度而跳过时间点。

```text
待发送 → 发送中 → 已暂停 → 发送中 → 已完成
             ├→ 已停止
             └→ 发送失败
```

暂停和失败时持久化当前游标；继续后从下一条未确认消息恢复。需要从头重新发送时创建新的发送任务，不能覆盖历史发送记录。

## 11. 用户和权限

第一阶段只提供两个固定角色，不开放用户自行注册：

| 角色 | 权限 |
|---|---|
| `ADMIN` | 创建和停用用户；管理模型版本和 MQTT 配置；查看、取消、复制、软删除全部任务；控制全部发送任务；查看操作记录 |
| `USER` | 创建仿真任务；查看、复制和取消自己的任务；查看自己的结果；控制自己任务的数据发送 |

已完成任务不能直接编辑。普通用户不能通过修改 URL 或直接调用接口访问其他用户任务。权限和数据归属必须在后端校验。

登录使用 Spring Security，密码使用 BCrypt 保存。浏览器登录状态使用 HttpOnly Cookie，会话持久化到 MySQL。关键操作记录操作人、时间、目标和结果，但不记录密码、Token、数据库凭据和完整敏感异常。

## 12. 校验和异常处理

### 12.1 参数校验

- 必填参数不能为空；
- 开始时间必须早于结束时间；
- 时间范围必须与步长形成完整序列；
- 基准模式强制使用模型版本绑定的时间、步长和参数；
- 场景参数符合类型、单位、范围和精度；
- 冷冻水供水温度低于回水温度；
- 水泵和电机效率处于 0～1；
- 窗墙比处于 0～1；
- 未启用或只读参数不能通过接口修改。

前端提供即时提示，后端执行最终权威校验。错误信息使用中文并指明参数名称、提交值和允许范围。

### 12.2 仿真异常

- 定期更新完成比例和当前模拟时间；
- 用户取消后安全停止，部分结果不能标记完成；
- TDengine 写入失败时记录已写入范围并清理不完整结果；
- 平台重启后将遗留运行任务标记异常中断；
- 普通用户看到中文摘要，详细堆栈只进入受控日志。

### 12.3 发送异常

- 网络临时中断时自动重连并有限重试；
- 连续重试超过限制后标记发送失败；
- 失败任务可以从持久化游标继续；
- `messageId` 在重试时保持不变；
- 接收端业务入库状态不由 MQTT PUBACK 推断。

## 14. 部署和配置

第一阶段部署组件为：

```text
Vue 3
Spring Boot 模块化单体
MySQL
TDengine
MQTT Broker
```

本地开发计划提供 Docker Compose 启动 MySQL、TDengine 和测试 MQTT Broker。正式环境可以连接已有 Broker。连接地址、账号、密码和环境差异通过外部配置提供，仓库只保存脱敏示例。

前端和后端使用同源部署入口，降低 Cookie、跨域和安全配置复杂度。日志至少包含任务编号、模型版本、阶段和错误摘要，不记录完整密码、Token 或未脱敏消息凭据。

## 15. 未来拆分路径

模块化单体必须提前满足：

- 仿真任务使用完整序列化参数快照；
- 引擎不依赖 Spring、数据库和协议；
- 任务执行通过 `SimulationExecutor` 边界；
- 结果写入通过明确端口；
- 数据发送只读取已入库结果；
- 任务领取和结果写入具备幂等约束；
- 跨模块数据对象带版本信息。

未来拆分计算 Worker 时：

```text
当前：任务服务 → 进程内执行器 → engine
未来：任务服务 → 任务队列 → 独立Worker → engine
```

主要变化是调度、通信、部署和监控，不重写仿真公式。全面微服务仍需要服务认证、网关、链路追踪、数据归属、分布式一致性和独立发布体系，只有在并发量、团队规模或独立部署需求明确后再单独设计。

## 16. 完成判断

设计进入实施后，只有同时满足以下条件才能把正式仿真平台标记为第一阶段完成：

1. 已实现并测试设计范围内的后端、前端和数据库功能；
2. Gaia 1.0 现有基准一致性没有退化；
3. 一周和全年任务均完成实际运行验证；
4. 图表、CSV 和 PNG 来自已入库结果；
5. MQTT 发送侧完成契约和回放测试；
6. 权限、异常和恢复场景通过；
7. 项目文档、运行说明和未验证事项已同步；
8. 代码经过任务分支、测试、提交、推送和 PR 流程。

`iot-platform-demo` 成功接收和入库不属于当前仓库第一阶段完成条件，而属于第二阶段跨项目联调验收。领导确认图表也不等同于模型物理合理性已经完成工程验收。
