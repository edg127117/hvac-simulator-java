# Gaia 1.1 模型接入设计

- 状态：已确认、待实施
- 原始 Python 运行状态：待建立兼容环境后验证
- 设计方式：针对性调整现有平台设计，不重写总体架构

## 1. 背景与目标

Gaia 1.1 是 Gaia 1.0 之后收到的第二个 Python 模型版本。它保留建筑、气象和 HVAC 主计算链，同时增加流量、温度和功率表的模拟测量过程，并输出由模拟测量值计算的制冷量和 COP。

本次设计的目标是明确 Gaia 1.1 如何进入现有纯 Java 引擎和未来正式仿真平台，确保：

- Gaia 1.0 已有复现结果和接口语义不被破坏；
- Gaia 1.1 的物理真值、模拟测量值和派生测量指标可以同时保存、展示和发送；
- 相同场景可以通过稳定的随机流规则重复运行；
- 后续 Python 版本继续按同一接入流程扩展，而不是重做整个平台。

本设计不代表 Gaia 1.1 已经完成 Python 基准冻结、Java 转换、测试或图表验收。

### 2.1 参数变化

Gaia 1.1 新增四个 HVAC 测量参数：

| 原始参数 | 含义 |
|---|---|
| `flow_noise_std` | 流量传感器相对噪声标准差，脚本注释单位为 `%` |
| `temperature_noise_std` | 温度传感器噪声标准差，单位为 `℃` |
| `sensor_bias` | 传感器固定偏差，原脚本未按流量和温度分别定义单位 |
| `power_meter_accuracy` | 功率表精度等级，计算中作为相对误差百分比使用 |

`BuildingEnvelope.R_wall` 已从 Gaia 1.1 删除。页面和任务快照必须按模型版本生成，Gaia 1.1 表单不能继续提交该已删除参数。

### 2.2 输出变化

Gaia 1.0 输出 17 个字段；Gaia 1.1 输出 30 个字段，新增 13 个字段：

| 类别 | 新增原始字段 |
|---|---|
| 物理真值 | `chw_flow_rate`、`cw_flow_rate`、`T_chw_return`、`T_cw_return`、`chiller_power_true_kW` |
| 模拟测量值 | `chw_flow_sensor`、`cw_flow_sensor`、`T_chw_supply_sensor`、`T_chw_return_sensor`、`T_cw_supply_sensor`、`T_cw_return_sensor` |
| 派生测量指标 | `measured_cooling_kW`、`measured_COP` |

### 2.3 同名字段语义变化

Gaia 1.1 不能只按字段名与 Gaia 1.0 对接：

- Gaia 1.0 的 `chiller_power_kW` 是理论冷机功率；Gaia 1.1 的同名字段是模拟功率表读数。
- Gaia 1.1 新增 `chiller_power_true_kW` 保存理论冷机功率。
- `chiller_COP` 仍是理论 COP；`measured_COP` 是模拟测量制冷量除以模拟功率表读数。
- Gaia 1.1 的 `total_power_kW` 是模拟测量冷机功率与理论辅助设备功率的合计，属于混合指标。

因此平台必须使用稳定的平台指标编码和来源类型，不能把 Python 原始字段名直接当成跨版本数据库列或 MQTT 契约。

### 2.4 图表变化

原脚本由三个子图扩展为五个子图：

1. 室内温度与室外温度；
2. 冷负荷与系统总功率；
3. 理论冷机功率与模拟测量冷机功率；
4. 理论 COP 与测量 COP；
5. 模拟测量的水系统温度。

## 3. 接入架构

### 3.1 总体流程

Gaia 1.1 在 `engine` 内部采用三段式计算：

```text
固定参数、时间和气象
  ↓
物理仿真层
  ├─ 建筑与室温状态
  ├─ 设备负荷和理论功率
  └─ 水流量与真实供回水温度
  ↓
测量模型层
  ├─ 流量传感器
  ├─ 温度传感器
  └─ 功率表
  ↓
测量派生层
  ├─ 测量制冷量
  ├─ 测量 COP
  └─ 混合系统总功率
  ↓
30 字段版本结果 → 指标映射 → 入库、图表、导出和发送
```

物理仿真层不依赖数据库、Web、MQTT 或测量展示。测量模型接收物理真值和确定性随机流，输出模拟仪表读数；派生层只根据本时间步已产生的测量值计算指标。该边界使后续测量模型升级不必改写建筑和设备公式。

### 3.2 Java 责任边界

计划在纯 Java `engine` 中增加 `measurement` 包，至少承担：

- 传感器偏差和噪声计算；
- 功率表相对误差计算；
- 不同随机子流的装配；
- 测量制冷量和测量 COP 的计算；
- 与 Gaia 1.1 兼容行为有关的数值保护。

Gaia 1.0 不调用该测量层，其已有结果类型和一致性测试保持不变。版本适配器负责把各模型的原始结果映射为平台统一指标，不让共享查询、图表或发送代码猜测字段语义。

## 4. 参数和页面设计

参数分组由模型版本目录动态提供：

- Gaia 1.0 保持已确认的十组参数表单；
- Gaia 1.1 增加第十一组“传感器与仪表”；
- `flow_noise_std`、`temperature_noise_std`、`sensor_bias` 和 `power_meter_accuracy` 以模型默认值装载为真实输入值；
- 场景模式允许修改已进入 Gaia 1.1 公式且通过范围校验的参数；
- 基准模式显示真实默认值但保持锁定；
- Gaia 1.1 不显示或提交已删除的 `R_wall`；
- 切换版本时丢弃旧版本参数并装载目标版本的完整参数集，不能展示两个版本参数的并集。

第一阶段仍允许在同一“新建仿真”页面中选择模型版本，不为 Gaia 1.0 和 Gaia 1.1 各建一套重复页面。

## 5. 指标语义和字段映射

### 5.1 来源类型

平台指标定义增加以下来源类型：

| 来源类型 | 含义 |
|---|---|
| `THEORETICAL` | 由物理模型或设备公式直接计算的理论值 |
| `SIMULATED_MEASUREMENT` | 对理论真值施加传感器或仪表误差后的模拟测量值 |
| `DERIVED_MEASUREMENT` | 由模拟测量值继续计算得到的指标 |
| `HYBRID` | 同时包含理论量和模拟测量量的组合指标 |

### 5.2 关键字段映射

| Gaia 1.1 原始字段 | 平台指标编码 | 来源类型 |
|---|---|---|
| `chiller_power_true_kW` | `chiller_power_theoretical_kw` | `THEORETICAL` |
| `chiller_power_kW` | `chiller_power_measured_kw` | `SIMULATED_MEASUREMENT` |
| `chiller_COP` | `chiller_cop_theoretical` | `THEORETICAL` |
| `measured_COP` | `chiller_cop_measured` | `DERIVED_MEASUREMENT` |
| `measured_cooling_kW` | `cooling_output_measured_kw` | `DERIVED_MEASUREMENT` |
| `total_power_kW` | `system_power_hybrid_kw` | `HYBRID` |
| `chw_flow_rate` | `chw_flow_theoretical_m3_s` | `THEORETICAL` |
| `chw_flow_sensor` | `chw_flow_measured_m3_s` | `SIMULATED_MEASUREMENT` |
| `cw_flow_rate` | `cw_flow_theoretical_m3_s` | `THEORETICAL` |
| `cw_flow_sensor` | `cw_flow_measured_m3_s` | `SIMULATED_MEASUREMENT` |
| `T_chw_return` | `chw_return_temperature_theoretical_c` | `THEORETICAL` |
| `T_chw_return_sensor` | `chw_return_temperature_measured_c` | `SIMULATED_MEASUREMENT` |
| `T_cw_return` | `cw_return_temperature_theoretical_c` | `THEORETICAL` |
| `T_cw_return_sensor` | `cw_return_temperature_measured_c` | `SIMULATED_MEASUREMENT` |

其余供水温度传感器字段也必须使用带 `measured` 语义的平台编码。完整映射在实施时作为版本资源登记并通过契约测试，不在业务代码中散落字符串判断。

Gaia 1.0 的 `chiller_power_kW` 继续映射到 `chiller_power_theoretical_kw`；不得因接入 Gaia 1.1 而回写或重解释历史结果。

## 6. 随机性和可复现基准

### 6.1 场景模式

Gaia 1.1 原脚本使用同一个 NumPy 全局随机序列生成气象、传感器噪声和功率表误差，且未固定种子。Java 场景模式采用更稳定但明确版本化的规则：

- 任务保存一个主随机种子；
- 根据固定算法派生气象、流量传感器、温度传感器和功率表子种子；
- 每类随机过程使用独立子流，增加一种测量指标不会改变既有气象序列；
- 任务同时保存随机流版本，派生算法升级后旧任务仍可重现；
- 相同模型版本、参数、时间范围、主种子和随机流版本必须产生相同结果。

### 6.2 Python 基准冻结

实施 Gaia 1.1 前先建立隔离且可记录依赖版本的 Python 环境，并完成：

1. 将原始 Python 文件和来源说明保存到 `reference/gaia-1.1`；
2. 在运行入口外固定 NumPy 主种子，不修改模型公式；
3. 冻结全部气象输入、30 字段输出和五联参考图；
4. 同时冻结各时间步的测量扰动，至少包括传感器误差和功率表相对误差；
5. Java 基准模式读取冻结气象与扰动，独立执行物理、测量和派生计算；
6. 对 30 个输出字段逐时间步比较，并按温度、流量、负荷、功率和 COP 分别定义容差。

只读取冻结的 30 字段结果再原样导出不能证明 Java 已完成转换。Java 必须独立计算，冻结结果只作为断言预期值。

## 7. 存储、图表和发送

### 7.1 存储

MySQL 保存模型版本、参数定义、指标定义、原始字段映射、指标来源类型、图表定义和任务随机流快照。TDengine 的核心宽表只接收跨模型语义稳定且经单独确认的指标；Gaia 1.1 新增的理论、测量、派生和混合指标优先进入扩展指标结构。

同一个时间点的真值和测量值必须使用不同 `metricCode`，不能只用显示名称区分。历史 Gaia 1.0 数据不迁移为测量值。

### 7.2 图表

平台继续提供温度、冷负荷、功率和 COP 四组核心图表，并根据 Gaia 1.1 图表定义增加：

- 理论与模拟测量冷机功率对比；
- 理论与测量 COP 对比；
- 冷冻水和冷却水模拟测量温度；
- 真实与模拟测量流量，作为可切换专属序列。

所有功率和 COP 序列按完整时间轴绘制连续曲线；停机零值和 Gaia 兼容的非零测量噪声不得被前端擅自删除。

### 7.3 MQTT 和后续协议

发送字段映射以平台指标编码为源。目标空调平台需要哪一类数据，由管理员配置映射；理论值、测量值和混合值不能共享同一个目标字段而不注明语义。目标平台暂不支持的 Gaia 1.1 指标仍完整保存在仿真平台。

该变化不要求修改仿真消息统一身份信息，也不改变“先入库、后发送”的流程。未来增加 HTTP、Kafka 或其他协议时继续复用同一指标目录。

## 8. 忠实兼容边界

以下行为先按 Gaia 1.1 实际执行代码冻结和复现，不在 Java 转换中静默修正：

- 真值为零时，传感器函数进入绝对高斯噪声分支，停机流量读数可能非零；
- 同一个 `sensor_bias` 被流量和温度测量共同使用，虽然两类量的单位不同；
- `total_power_kW` 混合模拟测量冷机功率和理论辅助设备功率；
- 测量制冷量以脚本实际执行表达式为准，不能根据与代码不一致的注释自行增加单位换算；
- Python 气象、传感器和仪表目前共用全局随机序列。

这些事项需要在基准报告中单独标记为“兼容行为、物理合理性待核验”。如后续决定修正，应发布新的模型版本并保留 Gaia 1.1 历史可复现能力。

## 9. 测试与验收

Gaia 1.1 实施完成至少需要：

- 原始 Python 在受控环境中成功运行，30 字段基准和五联图冻结完成；
- Java 对 30 个字段完成逐时间步对照，各类指标使用明确容差；
- 物理层、测量层和派生层分别具备公式、边界和异常测试；
- 固定任务重复运行结果一致，不同随机子流互不干扰；
- 零流量、停机功率、除零、NaN、无穷值和测量 COP 边界经过测试；
- Gaia 1.1 页面正确显示十一组参数，默认值是真实控件值，已删除参数不出现；
- 字段映射和来源类型契约测试通过，Gaia 1.0 历史语义保持不变；
- 核心图表和 Gaia 1.1 专属图表来自同一份已入库结果；
- CSV、PNG、数据库结果和 MQTT 字段映射分别验证；
- Gaia 1.0 现有完整测试继续通过。

自动化数值一致性、图表视觉验收、物理合理性验收和外部空调平台联调必须分别报告，不能互相替代。
