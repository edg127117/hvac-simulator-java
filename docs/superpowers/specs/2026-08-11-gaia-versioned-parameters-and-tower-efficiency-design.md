# Gaia 版本化参数目录与冷却塔效率接入设计

## 1. 目标

本任务在现有 Gaia 1.0/1.1 固定模型纵向切片上完成两项相互关联的能力：

1. 每个模型版本显式拥有独立参数目录，并在 API 与 Vue 页面标注“公共参数”和“版本专属参数”；
2. 使用 Gaia 1.1 已有的冷却水测量温度和气象湿球温度，接入中央空调平台既有 `TOWER_EFF` 计算、趋势和页面链路。

任务不修改 Gaia 物理公式、随机顺序、30 字段输出和冻结基准，不增加水泵压力、AHU 总压等 Gaia 1.1 无法提供的测点，也不修改自由拓扑平台设计。

## 2. 已确认边界

- 代码变更以 `hvac-simulator-java` 为唯一交付仓库；`iot-platform-demo` 已具备冷却塔三个测点合同、`TOWER_EFF_V1` 公式、趋势存储和页面展示，本任务只把它作为本地联调目标，不修改其代码。
- 冷却塔效率按与 WCR_COP 相同的证据层次验收：仿真值映射、MQTT 发布、中央平台接入、公式计算、趋势查询和页面曲线分别记录结果。
- 本地完整软件栈验收不代表真实现场 Broker、网络、凭据和生产部署已验收。
- 旧 MQTT 请求未声明指标集合时继续只发送 WCR_COP 四测点，避免现有调用方被动增加消息和失败点。

## 3. 版本化参数目录

### 3.1 参数归属语义

新增参数归属枚举：

- `COMMON`：多个模型版本都支持且代码、单位和业务语义相同的参数；各版本仍保存自己的真实默认值、范围和可编辑性，不要求默认值永久相等。
- `VERSION_SPECIFIC`：只属于当前模型版本或在该版本中具有独立语义的参数。

当前 Gaia 1.0 的目录包含 19 个公共物理与控制参数；Gaia 1.1 的目录包含同语义的 19 个公共参数和 4 个 Gaia 1.1 测量专属参数。后续版本如改变同名参数语义，应使用新代码或标记为版本专属，不能仅凭同名归入公共参数。

### 3.2 引擎目录结构

`ModelParameterDescriptor` 增加 `scope` 字段。`ModelReleaseCatalog` 不再把同一个 `physical` 列表直接拼给两个版本，而是分别构造 Gaia 1.0 和 Gaia 1.1 的不可变目录；公共参数定义可复用私有工厂，但每个发布版本拥有独立描述符列表和自己的默认值来源。

`applyOverrides(ModelVersion, Map<String, Double>)` 继续只接受所选版本目录内的代码。公共/专属标记只描述参数归属，不改变基准模式锁定、场景模式校验和实际配置快照行为。

### 3.3 API 与页面

参数 API 保持现有路径：

```text
GET /api/model-releases/{version}/parameters?mode=BASELINE|SCENARIO
```

返回的每个参数增加 `scope: COMMON|VERSION_SPECIFIC`，继续保留扁平 `parameters` 数组以兼容现有客户端。Vue 参数编辑器先按 `scope` 展示“公共参数”和“Gaia 1.0/1.1 版本专属参数”，再在每个区域内按现有 `group` 分组。

切换模型版本或模式时必须重新请求完整目录，并用该版本真实默认值整体替换当前表单；不同版本的草稿值不相互带入。Gaia 1.0 当前没有版本专属参数时显示明确空状态，不伪造差异。

## 4. 冷却塔效率 MQTT 合同

### 4.1 可选择指标

新增中央空调发送目标枚举：

```text
WCR_COP
TOWER_EFF
```

MQTT 创建请求增加 `targets` 和 `coolingTowerDeviceId`：

- `targets` 缺失时按旧合同解释为 `[WCR_COP]`；显式空集合或未知值拒绝；
- `deviceId` 继续表示冷水机组设备，默认 `WCR1`；
- `coolingTowerDeviceId` 表示冷却塔设备，默认 `TOWER1`；
- Vue 页面默认选择 `WCR_COP` 与 `TOWER_EFF`，并分别编辑冷机和冷却塔设备编号。

每个目标由独立映射方法产生测点，同一投递任务可以发送一个或两个目标。投递总消息数按实际生成的测点计算，不再假设每个时间步固定四条。

### 4.2 测点映射

Gaia 1.1 冷却塔映射为中央平台冻结来源编码：

| 中央平台来源测点 | Gaia 1.1 来源 | 语义 |
|---|---|---|
| `{towerDeviceId}_TCWin` | `coolingWaterReturnSensorC` | 冷却水从冷机回到冷却塔的进水测量温度，℃ |
| `{towerDeviceId}_TCWout` | `coolingWaterSupplySensorC` | 冷却塔出水送往冷机的测量温度，℃ |
| `{towerDeviceId}_TWB` | `wetBulbC` | 当前时间步气象湿球温度，℃ |

默认设备编号下分别为 `TOWER1_TCWin`、`TOWER1_TCWout`、`TOWER1_TWB`。中央平台现有别名配置会把它们解析为 `CT/TWin`、`CT/TWout`、`CT/TWB`，并按下式计算：

```text
TOWER_EFF = (TWin - TWout) / (TWin - TWB) * 100%
```

`TWB` 是 Gaia 已输出的气象输入，不冒充带随机噪声的温度传感器；文档和测试必须保留该来源区别。

### 4.3 运行状态约束

Gaia 1.1 在设备停止时仍保留默认冷却水温度，如果直接发送会使中央平台在冷却塔未运行时产生看似有效的效率。因此只有同时满足以下条件的时间步才生成冷却塔三个测点：

- `coolingTowerFanPowerKw > 0`；
- `coolingWaterFlowSensorM3PerSecond > 0`。

传感器温差或湿球关系异常时仍发送真实模拟测量值，由中央平台按既有公式记录输入异常，适配器不静默修正或裁剪。若请求只包含 `TOWER_EFF` 且所选范围没有运行时间步，创建投递时返回明确错误，不生成“零消息成功”任务。

## 5. 数据流与错误处理

完整链路为：

```text
版本选择 → 独立参数目录 → 场景参数快照 → Gaia 1.1 Java 结果
→ 按目标映射 WCR/冷却塔测点 → MQTT device/data/up
→ 中央平台别名与设备元数据 → TOWER_EFF_V1
→ 分钟结果与趋势接口 → 中央空调页面曲线
```

- 未知参数、跨版本参数和超范围值沿用现有稳定中文错误；新增未知参数归属不得被客户端自行推断。
- 未知发送目标、非法设备编号、Gaia 1.0 请求中央空调测点、无冷却塔运行点等在创建任务阶段拒绝。
- 单条 MQTT 发布失败仍只影响投递状态，不修改已完成的仿真结果。
- Broker 发布成功、中央平台接入成功、公式成功、趋势可查和页面可见分别验证，任何一层失败都不得描述为完整接入通过。

## 6. 测试与验收

### 6.1 参数目录

- 引擎测试断言两个版本分别构造独立目录，公共参数具有 `COMMON` 标记，Gaia 1.1 四个测量参数为 `VERSION_SPECIFIC`，Gaia 1.0 不接受测量参数覆盖。
- API 测试断言 `scope`、真实默认值、基准只读原因和场景可编辑状态。
- Vue 组件测试断言公共/专属两层展示、Gaia 1.0 空状态、切换版本重新加载且不串用参数值。
- 现有场景参数参与实际计算的测试继续通过。

### 6.2 冷却塔映射与发送

- 映射测试逐字段断言三个来源编码、设备编号、温度方向、湿球来源、时间戳、QoS 1 和非保留消息。
- 运行状态测试断言停止时间步不产生冷却塔点，运行时间步按中央公式可得到期望效率。
- 服务测试覆盖旧请求仍为四点、显式双目标的实际消息数、仅冷却塔目标、无运行点、Gaia 1.0 和非法目标。
- 完整 Maven 测试必须包含 Gaia 1.0 回归和 Gaia 1.1 全时间步 30 字段一致性，证明本任务没有改变模型结果。

### 6.3 前端与本地完整联调

- 前端执行类型检查、单元/组件测试、生产构建和 Playwright 端到端测试；页面显示两个指标选择项与两个设备编号。
- 新增独立冷却塔验收脚本，从参数或环境变量读取仿真平台、中央平台、Broker 和 JWT，不保存凭据。
- 脚本选择包含有效冷却塔运行点的连续真实仿真窗口，按实际发送的三个值计算预期效率，再逐分钟比较中央平台 `TOWER_EFF` 最新值和趋势；容差依据公式规模单独记录。
- 浏览器人工确认只证明本地页面曲线可见与布局正常；真实现场、长期运行和工程物理合理性继续标记未验证。

## 7. 兼容与非目标

- Gaia 1.0/1.1 CSV 字段、Python 冻结资产、随机抽样顺序、公式和图表不变。
- 参数 API 路径和既有字段不删除，只新增 `scope`。
- MQTT 旧请求默认行为保持 WCR_COP 四点；新页面显式请求两个目标。
- 不实现水泵效率、风系统耗功效率、自由拓扑画布、设备库、水力求解、数据库、权限或其他协议。
- 不修改 `iot-platform-demo`，不把本地联调结果写成真实现场验收。

## 8. 交付边界

本任务使用单一功能分支和 PR，按以下可审查边界提交：

1. 设计与实施计划；
2. 版本独立参数目录及 API；
3. Vue 公共/专属参数展示；
4. 冷却塔 MQTT 映射与发送目标；
5. 前端投递配置、自动化和本地完整联调脚本；
6. 实际状态文档与最终验证。

推送和 PR 前必须检查明确暂存文件、敏感信息、构建产物、完整测试结果和 `git diff --check`。PR 未合并前只描述为任务分支能力。
