# 文档生命周期与当前状态判定设计

## 1. 背景

仓库已经使用 `AGENTS.md`、`PROJECT_GUIDE.md`、`PROJECT_STATUS.md`、任务设计和实施计划分层记录规则、稳定事实、当前状态与历史决策。但现有规则仍有两个缺口：

- 已确认或已执行的设计、计划曾在后续任务中继续修改，历史记录不能稳定反映任务当时的边界；
- 旧计划中的未勾选项、旧设计中的未来描述可能被误当成当前未实现项，导致已经完成的能力被错误降级。

本次只整改文档治理规则和当前项目入口，不修改生产代码、测试、参考资产或任何既有 `docs/superpowers/specs`、`docs/superpowers/plans` 正文。

## 2. 目标

1. 已确认的设计和已批准的实施计划冻结，后续任务不得回写。
2. 新决策、新实现和状态变化通过新文档与当前入口承接，保留完整演进记录。
3. 后续开发从当前代码、测试、Git 和当前项目文档判断能力，不用旧记录推翻已完成事实。
4. `PROJECT_STATUS.md` 及时反映合并、完成、阻塞和验证状态，避免已经合并的任务仍被描述为未合并。

## 3. 非目标

- 不批量修改现有历史设计和计划，也不补写其复选框、完成说明或最新状态。
- 不删除、重命名或合并历史文档。
- 不增加 CI、Git Hook 或文档生成工具。
- 不改变模型、接口、参数、仿真结果或验收结论。

## 4. 文档角色与状态依据

### 4.1 当前有效入口

- `AGENTS.md`：长期硬规则、任务上下文入口和文档生命周期约束。
- `PROJECT_GUIDE.md`：稳定项目事实、当前正式设计导航、运行入口和长期边界。
- `PROJECT_STATUS.md`：当前完成项、未完成项、阻塞、风险、验证层级和下一步。

三个入口允许随项目演进更新，但每次更新必须以当前代码、测试、Git 和实际验证为证据，不能复制旧文档结论代替核验。

### 4.2 冻结历史记录

- `docs/superpowers/specs`：设计获得用户确认后冻结正文。
- `docs/superpowers/plans`：计划获得用户批准、进入实施后冻结正文。

冻结文档只说明任务当时的目标、约束、取舍和实施安排。未勾选步骤、未来时态和当时的未实现描述均不代表当前项目状态。

### 4.3 当前状态判定顺序

出现冲突时按以下顺序核验：

1. 当前代码、自动化测试、Git 合并关系和本轮实际验证证据；
2. `PROJECT_STATUS.md` 的当前完成、未完成和验证分级；
3. `PROJECT_GUIDE.md` 的稳定事实与当前正式设计导航；
4. 当前正式设计；
5. 冻结的历史设计和计划，仅作为背景证据。

旧文档不能单独把已有代码和测试支持的能力判定为“未实现”。反过来，设计完成、计划勾选或历史说明也不能单独证明功能已经实现或验收。

## 5. 冻结与承接规则

### 5.1 冻结后禁止回写

冻结的设计和计划不得因后续实现、测试、合并、状态修正、需求变化、术语调整或勘误而修改。后续任务也不得通过补勾复选框、追加“已完成”段落或改写未来描述同步现状。

### 5.2 新变化的承接方式

- 新设计决策：创建新的带日期设计文档，明确其补充、替代或废止的旧设计范围。
- 新实施任务：创建新的带日期计划，引用当前有效设计，不复制旧计划作为当前任务清单。
- 当前完成与验证变化：更新 `PROJECT_STATUS.md`。
- 稳定架构、运行入口或文档导航变化：更新 `PROJECT_GUIDE.md`。
- 旧文档存在错误或歧义：新建勘误或替代设计，并从 `PROJECT_GUIDE.md` 指向新文档；不修改旧正文。

### 5.3 任务开始与结束检查

任务开始时先读取 `AGENTS.md`，再按需读取 `PROJECT_GUIDE.md` 和 `PROJECT_STATUS.md`。只有当前入口明确导航到某份设计时，才把它作为当前正式边界；旧计划不得直接充当新任务需求。

任务交付前必须检查：

- 是否误改了既有 `docs/superpowers/specs` 或 `docs/superpowers/plans`；
- 当前完成、未完成、验证和合并状态是否已同步到 `PROJECT_STATUS.md`；
- 稳定事实或正式设计入口变化是否已同步到 `PROJECT_GUIDE.md`；
- 新文档是否清楚说明与旧文档的承接关系；
- 是否把历史记录、自动化测试、本地联调、现场验证等不同证据层级混为一谈。
